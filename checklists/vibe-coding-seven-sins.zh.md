# Vibe Coding 生存与七宗罪自查清单

**状态**: accepted baseline
**更新日期**: 2026-11-20
**English**: [vibe-coding-seven-sins.md](vibe-coding-seven-sins.md)
**实证来源**: [《Vibe Coding 生存指南》](https://fz.cool/vibe-coding-complete-guide/)（443 次真实项目会话、84 亿 Token 量化复盘）

> **核心结论**：结构不是速度的敌人，结构是速度的前提。小项目（`<5K` LOC、1–6 次会话）在可丢弃模式下成功率接近 100%；跨越相变临界点进入大项目（`>10K` LOC、50+ 次会话）后，缺乏结构会让成功率暴跌至约 55%，最大风险不是单次坏代码，而是跨会话的**一致性漂移**。

---

## 1. 先判断你的项目处于相变临界点哪一侧

| 维度 | 安全区（小项目 / 可丢弃模式） | 危险区（大项目 / 架构师模式） |
|---|---|---|
| 代码量 | `<5K` LOC | `>10K` LOC |
| 会话数 | 1–6 次会话 | 50+ 次会话 |
| 复杂度 | 单一领域 | 多系统集成（DB + 队列 + 前端 + 多 Agent） |
| 出错策略 | 重新生成比修复更快 | 必须定位根因并受控修复 |
| 必需控制 | 对话式快速迭代 | PRD / Task ID、Git Checkpoint、`/compact`、Gap Analysis、熔断器 |

## 2. 防住三大失败原型

- [ ] **沙箱墙（占失败约 60%）**：启动自主运行前先确认文件写权限、网络与工具可用性，绝不放任 Agent 在权限拒绝里空转几十轮。
- [ ] **上下文窗口耗尽（占失败约 25%）**：设立 **60 条消息硬熔断**并执行 `/compact`（超过 200+ 条消息后失败率从 `<10%` 飙升至 **35.7%**）；规划（Plan）与执行（Execute）分窗口进行。
- [ ] **安全过滤 / 能力配置天花板（占失败约 15%）**：复杂工程任务不禁用 thinking 模式；按任务形态分工（短闭环精准修复 vs 有界长程任务）。

## 3. 大型 Vibe Coding 七宗罪排查表

| # | 罪名 | 典型症状 | 必做对抗手段 |
|---|---|---|---|
| 1 | **宣布胜利，然后永远修** | 一天产出几十份“Phase Complete”，但主链路基础报错；把“代码存在”当“代码工作”。 | 以真实集成验证为准，不轻信文档宣称的完成百分比。 |
| 2 | **幽灵模块（Dead Code）** | 写出工整的 `pagination.py` / 异步 DB 层 / 共享类型，却没有任何调用方接入。 | **“接上或删掉”** + **“给我看调用者”**：新模块必须在当前会话内有真实调用方。 |
| 3 | **跨会话缝合怪架构** | 会话 1 写 `async def`，会话 2 注入同步 DB `Session`，会话 3 又加一套没人用的异步引擎。 | 会话结束前做单会话一致性检查，把架构规则下沉到 Lint/测试门禁。 |
| 4 | **大爆炸式重写** | Agent 一次重写数千行破坏隐蔽集成点，继续 Fix Forward 沉没数百轮消息。 | 单次重构拆小（目标 `<500` 行且每步可验证）；失控时果断 `git revert`。 |
| 5 | **太逼真的假数据** | 兜底函数返回逼真的模型名、指标或静态 Fixture，界面看着很专业却全是假数。 | 禁止生产路径静默回落假数据，读不到就明确显示“未知”或错误态。 |
| 6 | **沉睡的 Feature Flags** | 每个会话顺手加一个默认 `False` 的开关，核心功能开箱不可见且永不清理。 | **两周 Flag 审计**：连续两周仍为 `False` 的开关必须决策启用或删除（完整退役 Schema 见同级仓 `OpenAgenticSecurity/assurance-contracts`）。 |
| 7 | **文档的进步幻觉** | 宏大整洁的文档记录的是“愿望态”而非“实现态”，误导后续会话与新成员。 | 维护以证据为锚的 `STATUS.md`，以代码与工具输出而非文档措辞为准。 |

## 4. `>1K` LOC 仓库的 6 步标准会话结构

1. **Context Sync** — 读取 `STATUS.md`、`VIBE_CODING_CONTEXT.md` 与对应规范/契约。
2. **Gap Analysis** — 先让 Agent 对比设计文档与实际实现，列出差距。
3. **Plan-then-Do** — 生成分步计划并明确禁止占位符（如 `// TODO`、`coming soon`、空存根），人批准后再动手。
4. **Scoped Execution** — 小步推进，每次重要改动前保留 Git Checkpoint。
5. **Verification** — 跑真实的集成测试、单元测试与 Lint（Bug 往往藏在模块边界）。
6. **Checkpoint & Compact** — 提交清晰范围的改动，更新状态记忆，接近 60 条消息即 `/compact` 或重开新会话。

## 5. 实战 DOs & DON'Ts 速查

### DO

- [ ] **连续失败 3–5 次立即触发熔断**：停止盲目重试，人工介入做根因分析并重置上下文。
- [ ] 对每个新建工具模块严格执行 **“接上或删掉”** 与 **“给我看调用者”**。
- [ ] 在边界处优先补**集成测试**而非只写 mock 单元测试。
- [ ] 深层目录优先使用**绝对导入**，避免重构后相对路径大面积失效。
- [ ] 租户隔离（`tenant_id`）与资源生命周期等横切约束从第一行开始设计。
- [ ] Agent 熔断/循环检测按 **`(tool_id, normalized_params_hash)`** 追踪，不要只看 `tool_id`。

### DON'T

- [ ] 绝不写裸 `except Exception: pass` 把真实异常静默吞掉。
- [ ] 绝不硬编码 `localhost` 或本机绝对路径。
- [ ] 绝不接受合入带 `// TODO: implement` 的占位符存根。
- [ ] 绝不在 `async def` 路由或图节点中混入同步阻塞调用。
- [ ] 绝不遗留无人关闭的跨会话客户端/连接（HTTP / LLM / DB / SSH 必须使用 `with` / `async with`）。
- [ ] 绝不用情绪化语言催促 AI——直接提供完整 stack trace 并要求做 Root Cause Analysis。

## 6. 四条架构纪律

1. **推理与执行分层**：LLM 决策/规划平面与确定性代码执行/IO 平面保持清晰边界。
2. **资源生命周期显式管理**：谁创建谁关闭，统一使用上下文管理器。
3. **协议优于胶水代码**：用显式契约与协议替代重复桥接代码，降低跨会话认知税。
4. **架构变更先 Plan**：重大改造必须在新会话里先出计划、确认后再分步落地。
